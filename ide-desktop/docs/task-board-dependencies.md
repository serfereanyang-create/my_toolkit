# 任务板依赖与恢复

任务板执行前会检查完整依赖图。缺失依赖、重复编号、自依赖、循环依赖、损坏任务记录、活动租约和不一致的完成标记都会停止执行并保留原任务文件；系统不会为了让计划“能跑”而静默删除依赖或改写任务。

## 检查规则

- `dependsOn` 必须是非空字符串数组，依赖编号必须存在且不能指向自身。
- 编号必须唯一；模型计划中的显式重复编号会在持久化前拒绝。自动编号会避开显式编号。
- 依赖排序使用迭代拓扑检查，长链和密集依赖不会通过递归导致栈溢出。
- 有效租约代表另一个执行者正在运行；新的执行请求返回 busy，并保留原租约和任务文件。
- 已取消的任务板不会自动执行；必须明确重新打开任务。`in_progress` 的任务只有在没有有效租约时才进入恢复路径。
- 没有可执行任务但仍存在 pending / cancelled / blocked / in_progress 任务时，计划进入 blocked 并记录原因，不会显示完成。

界面使用同一套迭代图检查显示阶段。坏图只显示“依赖异常”和具体任务编号，隐藏继续、跳过等执行按钮；正常图的层级来自拓扑层级，不会因为深链递归崩溃。依赖错误、任务状态和租约文件都保留，便于用户修正后再次打开。

## 恢复边界

任务板确认前先做依赖检查，因此不会先创建 Git 分支再发现计划无效。继续、跳过和重新打开也会重新检查图。无 Git 工作区不会影响依赖检查；完成后的提交预览仅在仓库真实存在时执行。

取消执行返回 paused / cancelled，当前任务回到 pending，已经完成的任务保持 done。继续从当前任务开始，依赖任务按顺序执行；另一个会话的桥接、文件和任务板不会被触碰。

## 证据

- CLI `tests/task-graph.test.ts`：循环、缺失依赖、重复编号、长链、密集图、活动租约、取消状态、草稿和不一致完成标记。
- 桌面 `src/components/TaskBoardGraph.test.tsx`：坏图局部错误、无继续按钮、5000 节点迭代检查。
- `npm run test:app-tasks-ui`：真实 App 六个坏图场景，无模型调用、依赖不变、活动租约不被覆盖。
- `npm run test:app-workflows`：将依赖图、验证证据、暂停继续合入完整 App 流程。

测试使用带归属标记的本地任务板工作区和本地模型夹具；没有删除构建或测试证据。
